# План развития Qase Mobile

## Принцип работы

Этапы упорядочены по зависимостям: сначала безопасность и проверяемое текущее поведение, затем сеть, локальные данные и новые сценарии. Для каждого этапа указаны работа и критерий завершения. Изменения удобно выпускать небольшими pull request с записью принятых решений.

## Этап 0. Зафиксировать исходное состояние

### Что сделать

- Сохранить скриншоты всех текущих экранов и основных состояний.
- Описать существующие пользовательские сценарии: авторизация, список проектов, репозиторий, создание сущностей, просмотр и редактирование кейса.
- Составить карту текущих модулей и зависимостей.
- Зафиксировать известные ошибки и технический долг.
- Проверить, что проект собирается и существующие тесты запускаются.
- Не смешивать текущие незавершённые эксперименты с последующим редизайном.

### Почему сначала это

Скриншоты, воспроизводимая сборка и список сценариев дадут точку сравнения для последующих изменений.

### Результат этапа

- Документированное состояние «до».
- Повторяемая сборка.
- Список основных пользовательских сценариев.
- Начальный backlog с приоритетами.

## Этап 1. Закрыть безопасность и демо-режим

### Что сделать

- Немедленно отозвать API-токен, опубликованный в исходниках.
- Удалить секрет из текущего кода и публичной истории репозитория.
- Проверить проект на наличие других токенов и приватных данных.
- Оставить пользовательские токены только в Keychain.
- Заменить скрытый long tap на явную кнопку «Попробовать демо».
- Перевести демо-режим на локальные данные без обращения к реальному аккаунту Qase.
- Исключить токены из логов, сообщений об ошибках, тестов и аналитики.

### Почему это первый технический этап

Опубликованный токен даёт доступ к аккаунту вне приложения. Автономное демо позволит показывать проект без передачи учётных данных.

### Результат этапа

- В репозитории и сборке нет рабочих секретов.
- Демо полностью автономно.
- Обычная авторизация продолжает работать через персональный токен.

## Этап 2. Защитить существующее поведение тестами

### Что сделать

Сначала покрыть существующие сценарии, не меняя UI:

- построение URL и параметров пагинации;
- декодирование проектов, suites и cases;
- проверку и хранение токена;
- загрузку локальных demo-данных;
- отображение списка проектов;
- переход из проекта в repository;
- открытие test case;
- создание проекта и suite/case;
- logout;
- offline-запуск с ранее сохранёнными данными.

Добавить тестовые ответы для 401, 403, 404, 422, 429 и 5xx.

### Почему до рефакторинга

Тесты создадут безопасную границу для последующих архитектурных изменений. Они также покажут работодателю, что ты умеешь работать с legacy-кодом, а не только писать проект с нуля.

### Результат этапа

- Критические сценарии воспроизводимы автоматически.
- Тесты не требуют настоящего Qase API.
- Ошибки можно отличить от изменений поведения.

## Этап 3. Привести в порядок сетевой слой

### Что сделать

- Разделить построение запроса, выполнение, декодирование и интерпретацию ошибок.
- Ввести единое представление сетевых ошибок.
- Корректно различать:
  - неправильный или истёкший токен;
  - недостаточные права;
  - validation errors;
  - отсутствующую сущность;
  - rate limit;
  - недоступность сервера;
  - отсутствие интернета;
  - отмену запроса.
- Реализовать обработку `Retry-After` для 429.
- Не повторять автоматически небезопасные create/update/delete-запросы.
- Добавить отмену запросов при закрытии экрана.
- Унифицировать limit/offset pagination.
- Исключить дублирующиеся запросы и повторное добавление сущностей.
- Сделать сеть полностью подменяемой в тестах.

### Почему сейчас

Все дальнейшие функции зависят от API. Если начать добавлять runs, defects и attachments поверх текущего слоя, количество дублирования и ошибок быстро вырастет.

### Результат этапа

- UI получает понятные состояния, а не произвольные ошибки.
- Пагинация работает одинаково для разных сущностей.
- Сетевой слой тестируется без реального сервера.
- 401, 403, 422 и 429 приводят к разному UX.

## Этап 4. Перестроить локальные данные и offline-поведение

### Что сделать

- Определить Realm-данные как временный кэш, а не источник истины.
- Заменить Realm на SwiftData.
- Хранить:
  - проекты;
  - suites и cases;
  - дату последней синхронизации;
  - recent и favorite items;
  - черновики форм;
  - локальные вложения, ожидающие отправки.
- Показывать кэш сразу, а затем обновлять его из сети.
- Отмечать устаревшие данные и время последнего обновления.
- Не удалять весь кэш при обычном завершении приложения.
- Не выполнять скрыто create/update/delete после восстановления сети.
- В offline-состоянии разрешать чтение и создание черновиков, но отправлять изменения только после явного подтверждения пользователя.

### Почему до редизайна

Новый UI должен проектироваться сразу под loading, cached, refreshing, offline и failed states. Если сначала нарисовать только happy path, экран придётся переделывать.

### Результат этапа

- Список ранее загруженных проектов и кейсов доступен offline.
- Кэш не блокирует main thread.
- Пользователь понимает актуальность данных.
- Черновик не теряется при закрытии формы.

## Этап 5. Определить новую информационную архитектуру

### Целевая структура

- **Home** — обзор выбранного проекта, последние кейсы, активные runs и дефекты.
- **Repository** — иерархия suites и cases.
- **Work** — plans, runs, results и defects.
- **Settings** — аккаунт, demo mode, язык, кэш и диагностика.
- **Search** — системная глобальная точка входа, а не пустая вкладка.

### Что спроектировать

- Пользовательские пути между разделами.
- Выбор текущего проекта.
- Поведение back navigation.
- Deep links к project, case и run.
- Различия iPhone и iPad.
- Permission-aware действия: недоступные операции должны объяснять нехватку прав.
- Состояния каждого экрана до визуального дизайна.

### Почему перед визуальным редизайном

Карта переходов определит, где нужны поиск, выбор проекта и возврат к предыдущему уровню. После этого можно проектировать вид экранов.

### Результат этапа

- Карта экранов и переходов.
- Перечень состояний каждого экрана.
- Прототип основных сценариев без детальной стилизации.

## Этап 6. Создать UI foundation и постепенно обновить экраны

### Порядок экранов

1. Авторизация и demo entry.
2. Home.
3. Список проектов.
4. Repository.
5. Просмотр test case.
6. Создание и редактирование case/suite.
7. Settings.
8. Новые Work-сценарии.

### Общие изменения

- Единая система цветов, typography, spacing, corner radius и состояний контролов.
- Светлая и тёмная темы.
- Единые компоненты loading, empty, offline, error и permission denied.
- Системные навигационные элементы вместо самодельных там, где это возможно.
- Чёткая визуальная иерархия вместо плотных таблиц.
- Контекстные действия вместо постоянно открытой красной зоны удаления.
- Валидация рядом с полем, а не только общим alert.
- Отображение несохранённых изменений.
- Полное устранение смешения русского и английского.

### Разделение UIKit и SwiftUI

- Существующие сложные repository-навигацию и списки развивать на UIKit.
- Новые dashboard, формы и Work-флоу делать на SwiftUI.
- Выбирать UIKit или SwiftUI по задаче экрана и уже существующему коду.
- Не переписывать работающий UIKit только ради увеличения количества SwiftUI.

### Почему обновлять постепенно

Последовательная замена экранов сохраняет рабочее приложение и позволяет сравнивать старое и новое поведение после каждого шага.

### Результат этапа

- Цельный интерфейс без визуального смешения старых и новых компонентов.
- Одинаковые состояния ошибок и загрузки.
- Осмысленное использование обеих UI-технологий.

## Этап 7. Завершить Repository как полноценную функцию

### Что добавить

- Полный CRUD projects, suites и cases.
- Иерархическое раскрытие suites.
- Поиск и фильтрацию.
- QQL search.
- Steps, expected results и attachments.
- Custom fields и system fields.
- Shared steps и shared parameters.
- Favorites и recent cases.
- Удобное отображение длинного форматированного текста.
- Предупреждения и подтверждения destructive actions.

### Почему Repository раньше runs

Repository уже используется для работы с тестовой документацией. Завершённые создание, поиск и навигация дадут основу для выбора кейсов в runs.

### Результат этапа

Пользователь может полноценно работать с тестовой документацией без web-интерфейса Qase.

## Этап 8. Выполнение тестового запуска с телефона

### Последовательность

1. Список test plans.
2. Список runs.
3. Детали run и общий прогресс.
4. Последовательное выполнение test cases.
5. Установка статуса результата.
6. Комментарий и время выполнения.
7. Создание defect из failed result.
8. Завершение run.
9. История результатов.

### UX

- Один тест-кейс на экране во время выполнения.
- Быстрые статусы passed/failed/blocked/skipped.
- Прогресс и возможность вернуться к незавершённому кейсу.
- Автоматическое заполнение defect данными из failed result.
- Явное подтверждение завершения run.
- Сохранение локального черновика результата при прерывании приложения.

### Почему это главный новый сценарий

Сценарий связывает планы, запуски, результаты и дефекты. Пользователь проходит кейсы последовательно и может продолжить прерванную работу.

### Результат этапа

Полный путь project → run → case → result → defect выполняется с телефона.

## Этап 9. Добавить media workflow

### Что сделать

- Фото evidence для result или defect.
- Выбор существующего изображения.
- При необходимости короткое видео или аудиокомментарий.
- Предпросмотр перед загрузкой.
- Сжатие крупных файлов.
- Отображение прогресса загрузки.
- Повтор загрузки после ошибки.
- Безопасное хранение незагруженного файла.
- Корректная обработка отказа в camera/photo/microphone permission.

### Почему AVFoundation уместен здесь

Фото, видео и аудио нужны как вложения к результату или дефекту. Захват медиа следует добавлять вместе с предпросмотром, разрешениями и повтором загрузки.

### Результат этапа

Пользователь прикладывает evidence к результату или дефекту непосредственно во время тестирования.

## Этап 10. Accessibility, localization и iPad

### Что проверить

- VoiceOver для всех основных сценариев.
- Максимальный Dynamic Type.
- Контраст текста и статусов.
- Reduce Motion.
- Landscape.
- Аппаратную клавиатуру.
- Русскую и английскую локализации.
- Длинные переводы.
- Пустые и очень длинные названия.
- iPad split view для Repository и Work.
- Сохранение выбранного элемента при изменении размера окна.

### Почему отдельным этапом

Accessibility должна учитываться при создании компонентов, но отдельный аудит нужен после объединения всех основных сценариев.

### Результат этапа

Основные действия доступны без зрения, интерфейс не ломается на крупных шрифтах и использует пространство iPad.

## Этап 11. Наблюдаемость и производительность

### Что сделать

- Структурированные логи без приватных данных.
- Отдельные категории для network, persistence, sync и UI.
- Измерение:
  - запуска;
  - первого появления cached content;
  - полной синхронизации;
  - открытия большого repository;
  - загрузки attachment.
- Проверить список минимум с 1000 кейсами.
- Исключить декодирование изображений и тяжёлую обработку на main thread.
- Подключить MetricKit для диагностики hangs, crashes и launch performance.

### Целевые критерии

- Cached content появляется не позднее 500 мс на выбранном тестовом устройстве.
- Прокрутка большого списка не имеет заметных зависаний.
- Закрытый экран не продолжает ненужную загрузку.
- Логи позволяют восстановить причину ошибки без раскрытия токена.

## Этап 12. CI и оформление инженерного проекта

### CI

Для каждого pull request запускать:

- сборку;
- unit-тесты;
- integration-тесты;
- минимальный UI smoke suite;
- static analyzer;
- проверку отсутствия секретов.

### README

Добавить:

- понятное описание проблемы и аудитории;
- актуальные скриншоты;
- короткое demo-видео;
- архитектурную диаграмму проекта;
- описание offline-поведения;
- описание безопасности токена;
- поддерживаемые Qase-сущности;
- тестовую стратегию;
- измеренные показатели производительности;
- раздел «Trade-offs and decisions»;
- roadmap и известные ограничения.

### Почему это важно

README должен дать читателю возможность быстро понять задачи приложения, устройство основных частей, ограничения и способ проверки качества.

## Этап 13. Опциональный Foundation Models

Начинать только после завершения основного продукта.

### Первый рекомендуемый сценарий

Создание редактируемого черновика test case из краткого описания:

- title;
- description;
- preconditions;
- steps;
- expected results.

### Ограничения

- Только on-device обработка.
- Проверка доступности модели.
- Полностью рабочий ручной fallback.
- Никакой автоматической отправки результата.
- Пользователь всегда просматривает и редактирует draft.
- Не передавать модели токен или лишние данные аккаунта.
- Добавить тесты на формат результата, отмену и недоступность модели.

### Почему AI последний

Черновик от модели полезен после того, как ручное создание кейса и выполнение запуска работают стабильно. Пользователь всегда проверяет результат перед сохранением.

## Финальные критерии проекта

Проект можно считать готовым к портфолио, когда:

- в нём нет опубликованных секретов;
- demo работает без сети и аккаунта;
- Repository и Mobile Test Run проходят от начала до конца;
- offline-состояния понятны пользователю;
- UIKit и SwiftUI используются осмысленно;
- SwiftData обеспечивает кэш и черновики;
- media является частью result/defect workflow;
- все основные сценарии покрыты тестами;
- CI стабильно проходит;
- VoiceOver и Dynamic Type поддержаны;
- README объясняет не только возможности приложения, но и твои инженерные решения;
- AI остаётся дополнительным преимуществом, а не условием работы продукта.

## Принятые допущения

- Текущий deployment target приложения — iOS 18.6.
- UIKit сохраняется, SwiftUI добавляется постепенно.
- SwiftData заменяет Realm после появления тестовой защиты.
- Новые Qase-сущности добавляются только после стабилизации network и persistence.
