# План развития Qase Mobile

Этапы сохраняют принятый порядок зависимостей: безопасность и защита поведения → сеть → локальные данные → интерфейс → **Repository → выполнение Runs → media**. Foundation Models — последний опциональный этап после завершения основного продукта. Изменения следует выпускать небольшими PR с записью решений.

## Текущее состояние по исходникам

- Есть авторизация персональным токеном с Keychain, явный демо-вход и локальные mock-данные; смена credentials инвалидирует старую сессию. Это не подтверждает отзыв ранее опубликованного токена или очистку публичной истории: эти действия требуют отдельной проверки.
- Подключены Home, Repository, Work и Settings; выбор проекта, иерархия и поиск suites/cases, создание проекта/suite/case, удаление project/suite/case, редактор case и выбор родителя. Runs/Defects имеют списки и детали для чтения. Шаги case пока доступны только для чтения. Редактор существующего suite ещё предстоит реализовать.
- Сеть имеет подменяемый транспорт, каталог операций API v1, HTTP-ошибки с кодом и числовым `Retry-After`, пагинацию и защиту от поздних ответов. Единый permission/validation/rate-limit UX и политика retry ещё требуют завершения.
- Локальный слой использует **Realm**, кеш разделён по владельцу и проекту. Есть снимки Home, сохранённые сущности, последние кейсы и маркеры полноты каталога. Два черновика suite/case сохраняются в пределах открытой формы; это не долговременное сохранение после завершения приложения. Частичный успех последовательного сохранения не должен повторно создавать уже сохранённую сущность.
- В репозитории есть исходники unit/UI-проверок и workflow CI. Их наличие не подтверждает успешный прогон. Сборка, компиляция, тесты и CI при очистке документации не запускались; визуальная приёмка остаётся отдельной задачей пользователя.

Основания статусов: [сборка экранов](../QaseAPIProj/Classes/FeatureScreenFactory.swift), [сеть](../QaseAPIProj/Data/APIManager.swift), [Realm-кеш](../QaseAPIProj/Data/Database/RealmDB.swift). Подробности текущих границ — в [архитектуре](ARCHITECTURE.md), перечень проверок — в [разработке](DEVELOPMENT.md).

## Этапы и критерии завершения

### 0. Зафиксировать исходное состояние

Сохранить скриншоты экранов и loading/empty/offline/error-состояний, список сценариев и известных ошибок. Карта модулей описана в документации; её нужно поддерживать по коду. Незавершённые эксперименты не смешивать с редизайном.

**Готово, когда:** есть сравнимое состояние «до», приоритетный backlog, а пользователь подтвердил воспроизводимую сборку и запуск имеющихся тестов.

### 1. Завершить безопасность и демо

Подтвердить отзыв ранее опубликованного API-токена и удаление секрета из публичной истории; проверить другие секреты и приватные данные. Сохранить пользовательские credentials только в Keychain, исключить их из логов, ошибок, тестов и аналитики. Явный демо-вход и локальные данные уже есть по коду; автономность нужно проверить запуском.

**Готово, когда:** в репозитории и сборке нет рабочих секретов, отзыв и очистка истории подтверждены, demo работает без сети и реального аккаунта, персональная авторизация работает.

### 2. Защитить существующее поведение

Проверить и дополнить имеющиеся тесты URL/пагинации, декодирования, credentials, demo, проектов, Repository, case, создания сущностей, logout и offline-запуска. Сохранить регрессии изоляции owner/project, смены сессии, полноты кеша, отмены запросов, двух черновиков и частичного сохранения. Ответы 401/403/404/422/429/5xx должны иметь тестовые фикстуры.

**Готово, когда:** критические сценарии воспроизводимы автоматически без реального Qase API и пользователь подтвердил прогон. Только затем начинать миграцию хранилища.

### 3. Завершить сетевой слой

Сохранить разделение URL, транспорта и декодирования. Различать invalid token, permission denied, validation, not found, rate limit, server failure, offline и cancellation в UI. Завершить обработку `Retry-After`, единый limit/offset и отмену ненужной загрузки при закрытии экрана; исключить дубли запросов и сущностей. Не повторять автоматически небезопасные create/update/delete.

**Готово, когда:** сеть полностью подменяется в тестах, пагинация единообразна, 401/403/422/429 имеют разные понятные состояния, отменённый или устаревший ответ не публикуется и не записывается в кеш/историю.

### 4. Заменить Realm на SwiftData и завершить offline

**SwiftData заменяет Realm после тестовой защиты поведения; это принятое направление.** Сохранить кеш как производные данные, изоляцию owner/project и маркеры полноты. Хранить проекты, suites/cases, дату синхронизации, recent/favorites, долговременные черновики и ожидающие загрузки файлы. Показывать кеш сразу с последующим обновлением, возрастом данных и явными offline-состояниями; не очищать весь кеш при обычном завершении приложения. В offline разрешать чтение и черновики, отправку — только по явному подтверждению, без скрытого выполнения mutations после восстановления сети.

**Готово, когда:** ранее загруженные сущности доступны offline, обработка кеша не блокирует main thread, актуальность данных понятна, черновики переживают закрытие формы/приложения, миграция сохраняет защищённые инварианты.

### 5. Завершить информационную архитектуру

Развивать имеющиеся Home/Repository/Work/Settings; глобальный Search должен стать системной точкой входа. Спроектировать переходы, выбор проекта, back navigation, deep links project/case/run, iPhone/iPad и permission-aware действия. Сначала описывать состояния экранов, затем визуальное оформление.

**Готово, когда:** карта переходов, перечень состояний и прототип основных сценариев согласованы, недоступные операции объясняют недостаток прав.

### 6. Завершить UI foundation и обновление экранов

Порядок: авторизация/demo → Home → проекты → Repository → просмотр case → создание/редактирование case/suite → Settings → новые Work-сценарии. Использовать общие цвета, typography, spacing, радиусы и состояния из [дизайн-системы](../Design/DESIGN_SYSTEM.md). Нужны light/dark, loading/empty/offline/error/permission denied, системная навигация, контекстные destructive actions, полевая валидация и предупреждение о несохранённых изменениях. Завершить RU/EN без смешения языков.

Сложные списки и навигацию Repository развивать на UIKit; новые dashboard, формы и Work использовать на SwiftUI там, где это соответствует уже существующему коду и задаче. Работающий UIKit не переписывать ради количества SwiftUI.

**Готово, когда:** интерфейс цельный, состояния и ошибки единообразны, экранные сценарии прошли пользовательскую визуальную приёмку. Дизайн-концепты сами по себе не подтверждают результат приложения.

### 7. Завершить Repository

Довести полный CRUD projects/suites/cases, иерархическую навигацию, поиск/фильтры и QQL. Добавить редактирование steps/expected results, attachments, custom/system fields, shared steps/parameters, favorites и удобное отображение длинного форматированного текста. Сохранить recent cases и подтверждения destructive actions.

**Готово, когда:** тестовая документация полноценно создаётся, находится, редактируется и удаляется с телефона без web-интерфейса Qase. Завершение Repository предшествует выполнению runs.

### 8. Выполнение тестового запуска

Развить чтение Runs в полный путь: plans → runs → детали/прогресс → последовательное выполнение cases → result/status → комментарий и время → defect из failed result → подтверждённое завершение run → история результатов. Во время выполнения показывать один case, быстрые passed/failed/blocked/skipped, возврат к незавершённому case и локальный черновик результата после прерывания приложения. Defect предзаполнять из failed result.

**Готово, когда:** путь project → run → case → result → defect выполняется с телефона, прерванную работу можно продолжить, завершение run требует явного подтверждения.

### 9. Media workflow

После выполнения Runs добавить фото evidence и выбор существующего изображения для result/defect; при необходимости — короткое видео/аудио. Захват через AVFoundation должен включать предпросмотр, сжатие, прогресс, повтор после ошибки, безопасное хранение ожидающего файла и обработку отказа camera/photo/microphone permission.

**Готово, когда:** evidence прикладывается непосредственно во время тестирования, не теряется при прерывании и имеет понятные состояния загрузки/отказа.

### 10. Accessibility, localization и iPad

Учитывать доступность при создании компонентов и провести общий аудит после объединения сценариев: VoiceOver, максимальный Dynamic Type, контраст, Reduce Motion, landscape, аппаратная клавиатура, RU/EN, длинные переводы и крайние длины названий. Реализовать iPad split view Repository/Work с сохранением выбора при изменении окна.

**Готово, когда:** основные действия доступны без зрения, крупный текст не ломает интерфейс, iPad использует доступное пространство.

### 11. Наблюдаемость и производительность

Добавить структурированные логи network/persistence/sync/UI без приватных данных и MetricKit. Измерять запуск, появление кеша, синхронизацию, открытие большого Repository и attachment upload. Проверить минимум 1000 cases; тяжёлую обработку и декодирование изображений вынести с main thread.

**Готово, когда:** cached content появляется за ≤500 мс на выбранном устройстве, прокрутка не имеет заметных зависаний, закрытый экран не продолжает ненужную загрузку, причину ошибки можно восстановить без раскрытия токена.

### 12. Завершить CI и оформление проекта

Существующий workflow содержит сборку, unit/UI-прогоны и артефакты. Довести PR-проверки до build, unit/integration, минимального UI smoke, static analyzer и поиска секретов; стабильность подтвердить отдельно. Развивать README актуальными скриншотами приложения, demo-видео, архитектурной диаграммой, offline/security, поддерживаемыми сущностями, тестовой стратегией, измеренной производительностью, решениями и ограничениями.

**Готово, когда:** CI стабильно проходит, README отражает подтверждённые возможности и измерения. Запуск CI и сборок не входит в очистку документации: согласно AGENTS.md приложение проверяет пользователь.

### 13. Опциональный Foundation Models

Начинать после завершения основного продукта. Первый сценарий — редактируемый черновик case из краткого описания: title, description, preconditions, steps, expected results. Только on-device, с проверкой доступности, ручным fallback и тестами формата/отмены/недоступности. Не передавать token или лишние account data; не отправлять результат автоматически, пользователь просматривает и редактирует draft.

**Готово, когда:** дополнительный сценарий не нарушает ручную работу и не является условием доступности продукта.

## Готовность к портфолио и принятые допущения

Проект готов к портфолио после подтверждения отсутствия опубликованных секретов, автономного demo, полного Repository и Mobile Test Run, понятного offline, SwiftData-кеша/черновиков, evidence workflow, тестовой защиты и стабильного CI, VoiceOver/Dynamic Type и README с инженерными решениями. AI остаётся дополнительной возможностью.

Текущий deployment target — iOS 18.6. UIKit сохраняется, SwiftUI развивается постепенно. SwiftData заменяет Realm после защиты поведения; новые сценарии Qase подключаются после стабилизации сети и persistence. Наличие маршрута в [API-каталоге](API_V1.md) не является критерием завершения пользовательской функции.
